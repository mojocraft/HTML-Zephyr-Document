    Q 引脚使用中，pinctrl 和 GPIO 以及外设（UART/CAN/SPI）的关系是怎样的？什么情况下需要写 pinctrl？ ▶

    一句话：pinctrl 决定"这个引脚用来干什么"，GPIO 是其中一种选项。

    1
    外设驱动层 — UART / CAN / SPI / I²C
    使用引脚通信，不关心引脚的物理细节。调用 uart_tx() / can_send() 即可
    2
    pinctrl 层 — 引脚控制
    决定引脚分配给谁、配置电气属性（上下拉、驱动强度）。STM32 这里就是 AF 寄存器
    3
    GPIO 层 — 通用输入输出
    最底层的引脚操作。一个引脚同一时刻只能归一层所有
    场景
    STM32
    ESP32
    需要 pinctrl？
    必须写 — 要设 AF 寄存器
    通常不需要 — GPIO Matrix 自动路由
    写法
    pinctrl-0 + STM32_PINMUX('C',10,AF7)
    tx-pin = <43>; rx-pin = <44>;
    电气属性
    也在 pinctrl 节点里写
    在 pinctrl 或直接 bias-pull-up
    共同点：无论哪个平台，bias-pull-up / drive-strength / slew-rate 这些电气属性都归 pinctrl 管
    💡 关键约束：一个引脚的归属链路是 pinctrl 决定它属于谁 → 外设驱动使用它 → 你不能同时拿它当 GPIO。如果 CAN_RX 已经分配给 CAN 控制器，就不能用 gpio_pin_get() 去读它，除非先 pinctrl 切回 GPIO 模式。
    pinctrlGPIOSTM32ESP32devicetree
    Q 简单设备（LED/按键）用 gpios，复杂外设（UART/CAN）用 pinctrl-0，能否这样理解？ ▶

    完全正确。区分规则就一句话：

    简单设备 — LED / 按键
    devicetree 写 gpios
    ▼ GPIO 驱动自动 pinctrl
    ▼ gpio_pin_set()
    gpio_pin_interrupt()
    复杂外设 — UART / CAN / I²C
    devicetree 写 pinctrl-0
    ▼ 手动指定 AF / pinmux
    ▼ uart_tx()
    can_send()
    ℹ️ 判断标准：你只需要高低电平/读输入状态 → gpios；你需要通信协议 → pinctrl-0 + pinmux。ESP32 是个例外，因为有 GPIO Matrix，复杂外设也常用 tx-pin / rx-pin 简化写法。
    gpiospinctrldevicetreeSTM32ESP32
    Q 自定义设备时，如何确定在设备树中应该写哪些属性？以 SPI 传感器、I²C 显示屏、CAN 设备为例 ▶

    核心方法：每个 compatible 对应一个 YAML 绑定文件，绑定文件里声明了所有合法属性。

    compatible → dts/bindings/*.yaml → 读 properties + include 继承链
    设备类型必需属性可选属性reg 含义
    SPI 传感器compatible, regirq-gpios, spi-max-frequencyCS 片选编号
    I²C 显示屏compatible, regreset-gpios, dc-gpiosI²C 7-bit 地址
    CAN 设备compatible (控制器)bitrate, sample-pointN/A — CAN 设备不在 DT 中描述
    ⚠️ CAN 的特殊性：CAN 总线上的设备通常不在 devicetree 中描述，Zephyr 没有像 I²C/SPI 那样的"CAN 设备"总线模型。只有 CAN 控制器本身在 DT 中配置，CAN 上的设备在应用层用 SocketCAN 通信。

    Q 设备树中节点标签后的 @address 和 reg 属性是什么关系？有 @xx 就必须有 reg 吗？ ▶
    核心规则
    • 节点名中的 @xxxx 叫 unit-address（单元地址）
    • 有 @address → 必须有 reg，且 reg 第一个值 == @ 的值
    • 无 @address → 不需要 reg
    • reg 的格式由父节点的 #address-cells 和 #size-cells 决定
    总线实例reg 第一个值含义
    I²Cssd1306@3c { reg = <0x3c>; }7-bit 从机地址
    SPIbme280@0 { reg = <0>; }CS 片选线编号
    Flashpartition@8000 { reg = <0x8000 0x1000>; }起始地址（第二个值是大小）
    GPIO 设备led_0 { gpios = <...>; }不需要 reg — 没有总线地址
    devicetreeregunit-address#address-cells

    Q 如何知道一个外设应该调用哪些 API？使用的标准流程是什么？ ▶

    三步定位法：compatible → 驱动 → 头文件 → Samples

    compatible → drivers/*.c → include/drivers/*.h → samples/drivers/

    Zephyr 外设 API 的统一使用模式：

    1
    设备树描述硬件
    在 .overlay 或 dts 中写好外设节点，包括 compatible、pinctrl、reg 等
    2
    获取设备实例
    DEVICE_DT_GET() 或 I2C_DT_SPEC_GET() 等宏从 DT 提取已配置好的设备
    3
    检查设备就绪
    device_is_ready() — 确认驱动初始化完成、硬件可访问
    4
    配置（可选）
    <periph>_configure() — 设置波特率、模式等运行时参数
    5
    使用外设
    <periph>_read/write/send() — 实际读写操作

    各外设 API 速查：

    外设头文件获取实例宏核心 API

    Q 自定义电路板时，需要在 boards/ 下创建哪些文件？各自起什么作用？STM32 和 ESP32-S3 双核有什么区别？ ▶

    核心思路：把芯片厂商已写好的 SoC 级文件重组，加上你板子特有的外设和引脚分配。

    单核板子（STM32）完整目录结构：

    boards/<vendor>/<board>/
├── board.cmake           # 烧录/调试工具配置（runner：OpenOCD/JLink/pyOCD）
├── board.yml             # 板子元数据（名称、厂商、SoC）
├── Kconfig.defconfig    # Kconfig 默认值的来源声明（固定文件名）
│
├── <board>.dts          # 板级设备树（LED/按键/传感器挂在哪）
├── <board>.yaml         # 板级绑定（支持的连接器/外设）
├── <board>_defconfig    # Kconfig 默认配置（选芯片型号 + 启用驱动）
├── Kconfig.<board>      # 声明 BOARD_XXX 符号
└── (可选) pre_dt_board.cmake  # 设备树预处理
    📄 Kconfig.<board>

    声明板子存在，让 -b myboard 能识别。文件名随板名变，如 Kconfig.fc_ddriver：

    config BOARD_MYBOARD
    bool "My Board"
    depends on SOC_STM32F407XE
    📄 Kconfig.defconfig

    默认 Kconfig 选项，格式 if BOARD → default XXX：

    if BOARD_MYBOARD
config I2C
    default y
endif
    📄 board.cmake

    烧录/调试工具（runner）配置，不管芯片选型：

    board_runner_args(openocd
  "--cmd-pre-init" "source [find ...]")
board_runner_args(jlink
  "--device=STM32F429IG" ...)
include(.../openocd.board.cmake)
include(.../jlink.board.cmake)

    芯片型号实际由 _defconfig 中 CONFIG_SOC_XXX=y 决定

    📄 board.yml

    板子元数据，给 west 和工具链用：

    board:
  name: myboard
  vendor: my-company
  socs:
    - name: stm32f407xe

    声明板子名称、厂商、SoC，供 west 和 IDE 识别

    myboard_defconfig

    .conf 格式（不是 Kconfig 语法）：

    CONFIG_SOC_STM32F407XE=y
CONFIG_CONSOLE=y
CONFIG_SERIAL=y
CONFIG_I2C=y

    启用板子需要的 SoC 型号和驱动

    myboard.dts — 板级设备树

    #include SoC dtsi + 写外设节点：

    #include <st/f4/stm32f407Xe.dtsi>

/ {
    chosen { zephyr,console = &usart1; };
    leds { led0 { gpios = <&gpioa 5 0>; }; };
};
&i2c1 { status = "okay"; };

    决定哪些外设启用、LED 接在哪个引脚

    双核板子（ESP32-S3）— 为什么结构不同：

    ESP32-S3 有两个 Xtensa 核各自独立运行，Zephyr 把每个核当作独立的"板子"：

    boards/<vendor>/esp32s3_myboard/
├── board.cmake              # 公共编译配置
├── board.yml
├── Kconfig.defconfig
├── Kconfig.<board>
│
├── esp32s3_myboard_procpu/          ← PROCORE (CPU0)
│   ├── esp32s3_myboard_procpu.dts   # Core 0 的设备树
│   ├── esp32s3_myboard_procpu.yaml
│   ├── esp32s3_myboard_procpu_defconfig
│   └── Kconfig.defconfig
│
├── esp32s3_myboard_appcpu/          ← APPCORE (CPU1)
│   ├── esp32s3_myboard_appcpu.dts
│   ├── esp32s3_myboard_appcpu.yaml
│   ├── esp32s3_myboard_appcpu_defconfig
│   └── Kconfig.defconfig
│
└── esp32s3_myboard_common.dtsi     ← 两个核共享的 DT

    为什么编译命令变成 -b espressif/esp32s3/myboard_procpu？

    Zephyr 的板子查找路径是 boards/<vendor>/<soc>/<board>。ESP32-S3 每个核各有一个子目录，必须精确指定到核级变体。而 STM32 是单核，目录结构就是 boards/<vendor>/<board>，直接用板名即可。

    对比
    STM32（单核）
    ESP32-S3（双核）
    目录结构
    boards/vendor/board/
    boards/vendor/soc/board_procpu/ + _appcpu/
    编译命令
    west build -b myboard .
    west build -b espressif/esp32s3/myboard_procpu .
    两个核差异
    N/A
    PROCPU 跑 Zephyr 内核 + 外设；APPCPU 被 PROCORE 启动，共享部分外设需 IPC。chosen 节点和中断分配不同

    快速创建方法：对照现有板子抄

    # 找到最接近你芯片的板子
ls zephyr/boards/st/nucleo_f407zg/

# 全目录复制
cp -r zephyr/boards/st/nucleo_f407zg/ boards/<your-vendor>/myboard/

# 然后逐一改：
#   Kconfig. → 内容: BOARD_MYBOARD, depends on SOC_XXX
#   myboard_defconfig → 改成你的 SoC 型号和需要的驱动
#   myboard.dts → 改 #include 的 dtsi，改 chosen，加你的外设
#   myboard.yaml → 改 identifier
#   board.yml → 改 name/vendor/socs
    ℹ️ 本质规律：SoC 级文件（dtsi、Kconfig）是芯片厂商写好的——你 #include 进来。板级文件（dts、defconfig）才是你的——你决定哪些外设启用、LED 接在哪个引脚。创建新板子就是"引用 SoC + 定制板级"。

    Q 定义了板级文件后直接 west build 就行吗？需要在工程根 CMakeLists.txt 中指定什么？ ▶

    分两种情况：

    板子位置需要额外配置？编译命令
    放在 Zephyr 源码 zephyr/boards/ 下不需要，自动发现west build -b myboard .
    放在你自己工程 boards/ 下 (out-of-tree)需要 — 加一行 BOARD_ROOTwest build -b myboard .

    Out-of-tree 板子的正确做法（工程根 CMakeLists.txt）：

    cmake_minimum_required(VERSION 3.20.0)

# 关键：APPEND = 追加到已有列表，不覆盖 Zephyr 内置路径
list(APPEND BOARD_ROOT ${CMAKE_CURRENT_SOURCE_DIR})

find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
project(my_app)

target_sources(app PRIVATE src/main.c)
    规则
    • list(APPEND BOARD_ROOT ...) 必须在 find_package(Zephyr ...) 之前
    • APPEND 是 CMake list() 的子命令，意思是追加到列表末尾。你不能用 set(BOARD_ROOT ...)，那会覆盖整个列表，导致 Zephyr 自带的板子全部丢失
    • BOARD_ROOT 是一个 CMake 列表变量，Zephyr 内置路径已经存在其中，你的路径只是追加进去
    • 你的 boards/<vendor>/<board>/ 目录结构必须遵循 Zephyr 约定
    • 如果你的板子名和 Zephyr 内置的重名，你的优先级更高（会覆盖内置的）

    也可以在命令行指定（不推荐，容易忘）：

    west build -b myboard . --board-root .
    💡 推荐把 BOARD_ROOT 写在 CMakeLists.txt 里，一劳永逸。你的 fc_ddriver 工程就是这么做的——第 4 行 list(APPEND BOARD_ROOT ${CMAKE_CURRENT_SOURCE_DIR}) 在 find_package 之前。
    boardCMakeBOARD_ROOTwestbuild
