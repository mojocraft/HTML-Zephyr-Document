    F 基础概念

    Q 引脚使用中，pinctrl 和 GPIO 以及外设（UART/CAN/SPI）的关系是怎样的？什么情况下需要写 pinctrl？ ▶

    一句话：pinctrl 决定"这个引脚用来干什么"，GPIO 是其中一种"干什么"的选项。

    三层架构：

    ┌──────────────────────────────────────┐
│  外设驱动 (UART/CAN/SPI/I²C)          │  ← 使用引脚，不关心引脚物理细节
├──────────────────────────────────────┤
│  pinctrl (pin control)               │  ← 把引脚分配给外设，配置电气属性
├──────────────────────────────────────┤
│  GPIO (通用输入输出)                   │  ← 直接操控引脚电平
└──────────────────────────────────────┘

    一个物理引脚同一时刻只能做一件事：要么是 UART_TX，要么是 CAN_RX，要么是普通 GPIO。pinctrl 就是负责做这个选择的。

    什么时候需要写 pinctrl？

    • STM32 — 必须写：STM32 的引脚功能由 AF（Alternate Function）寄存器决定。用 USART3_TX 必须把对应引脚的 AF 设为 AF7。
    • ESP32-S3 — 通常不需要显式写：ESP32 有 GPIO Matrix，几乎所有外设信号可以路由到任意 GPIO，驱动内部自动完成路由。只有需要 IO MUX（更低延迟）或特殊电气属性时才手动写。
    • 电气属性 — 总是 pinctrl 的职责：上下拉、驱动强度、压摆率等，无论 STM32 还是 ESP32 都属于 pinctrl 范畴。

    STM32 示例（必须显式 pinctrl）：

    /* STM32: 必须显式配置 pinctrl */
&usart3 {
    pinctrl-0 = <&usart3_tx_pc10 &usart3_rx_pc11>;
    pinctrl-names = "default";
};

&pinctrl {
    usart3_tx_pc10: usart3_tx_pc10 {
        pinmux = <STM32_PINMUX('C', 10, AF7)>;  /* AF7 = USART3_TX */
    };
    usart3_rx_pc11: usart3_rx_pc11 {
        pinmux = <STM32_PINMUX('C', 11, AF7)>;
    };
};

    ESP32-S3 示例（通常简化）：

    /* ESP32-S3: 通常只写这个就够了，驱动内部自动做 pinmux */
&uart0 {
    tx-pin = <43>;
    rx-pin = <44>;
};

    外设 vs GPIO vs pinctrl 关系总结：

    层级负责什么STM32ESP32
    pinctrl引脚功能选择 + 上下拉/驱动强度必须写 pinmux，指定 AF驱动自动处理，电气属性可加
    GPIO直接读写引脚、中断gpio_pin_set() / gpio_pin_interrupt()同左
    外设高层协议操作uart_tx() / can_send()同左

    关键约束：一个引脚的归属链路是 pinctrl 决定它属于谁 → 外设驱动使用它 → 你不能同时拿它当 GPIO。如果 CAN_RX 引脚已经分配给 CAN 控制器，就不能用 gpio_pin_get() 去读它，除非先把引脚从 CAN 断开重新 pinctrl 切回 GPIO 模式。

    Q 简单设备（LED/按键）用 gpios，复杂外设（UART/CAN）用 pinctrl-0，能否这样理解？ ▶

    这个理解完全正确。区分规则如下：

    简单设备（LED/按键）：      复杂外设（UART/CAN/I²C）：

devicetree 里写 gpios       devicetree 里写 pinctrl-0
      ↓                            ↓
GPIO 驱动自动 pinctrl       手动指定 AF/pinmux
      ↓                            ↓
gpio_pin_set() /             uart_tx() / can_send()
gpio_pin_interrupt()

    为什么简单设备不需要 pinctrl-0？

    gpios 属性本身就会触发 Zephyr 的 GPIO 驱动去自动配置引脚为 GPIO 模式。GPIO 是所有引脚最"原始"的功能，不需要额外的 Alternate Function 选择（或者说默认 AF 就是 GPIO），所以不需要手动写 pinctrl。

    具体在 devicetree 中的写法对比：

    /* LED：简单 GPIO 设备，只需要 gpios */
/ {
    leds {
        compatible = "gpio-leds";
        led0: led_0 {
            gpios = <&gpioa 5 GPIO_ACTIVE_LOW>;
            label = "Green LED";
        };
    };
};

/* 按键：同样只需要 gpios */
/ {
    buttons {
        compatible = "gpio-keys";
        button0: button_0 {
            gpios = <&gpioc 13 (GPIO_PULL_UP | GPIO_ACTIVE_LOW)>;
            label = "User Button";
        };
    };
};

/* UART：复杂外设，需要 pinctrl-0 */
&usart1 {
    pinctrl-0 = <&usart1_tx_pb6 &usart1_rx_pb7>;
    pinctrl-names = "default";
    status = "okay";
};

    判断标准：

    • 你只需要高低电平、读输入状态 → gpios 就够了
    • 你需要通信协议（串口/CAN/SPI/I²C）→ 必须 pinctrl-0 + pinmux
    • 中间地带：PWM 有时通过 GPIO 模拟，有时是硬件 PWM 控制器，后者也需要 pinctrl

    ESP32 的例外：ESP32 因为有 GPIO Matrix，即使复杂外设也常用 tx-pin/rx-pin 这种简化写法替代显式 pinctrl。但 STM32 几乎没有例外 — 非 GPIO 功能就必须写 pinctrl。

    gpiospinctrldevicetreeSTM32ESP32
    Q 自定义设备时，如何确定在设备树中应该写哪些属性？以 SPI 传感器、I²C 显示屏、CAN 设备为例 ▶

    核心方法：每个 compatible 字符串对应一个 YAML 绑定文件，绑定文件里声明了所有合法属性。

    查找属性的三步法：

    1. 确定设备的 compatible — 如 "st,lis2dh"，这是找到绑定的钥匙
    2. 找到对应的绑定文件 — 在 zephyr/dts/bindings/ 下按厂商/类型组织
    3. 读 YAML 的 properties — 还包括 include 继承链中的属性
    zephyr/dts/bindings/
├── sensor/
│   └── st,lis2dh.yaml          ← I²C/SPI 传感器绑定
├── i2c/
│   └── i2c-device.yaml          ← 通用 I²C 设备基类
├── spi/
│   └── spi-device.yaml          ← 通用 SPI 设备基类
├── can/
│   └── bosch,mcan.yaml          ← CAN 控制器绑定
└── vendor-prefixes.txt

    三种设备对照：

    设备类型必需属性可选属性
    SPI 传感器compatible, reg (CS 片选编号)irq-gpios, spi-max-frequency
    I²C 显示屏compatible, reg (I²C 7-bit 地址)reset-gpios, dc-gpios, width, height
    CAN 设备compatible (控制器已有绑定)bitrate, sample-point, bus-speed

    SPI 传感器实例（BME280）：

    &spi1 {
    pinctrl-0 = <&spi1_sck_pa5 &spi1_miso_pa6 &spi1_mosi_pa7>;
    pinctrl-names = "default";
    status = "okay";

    bme280@0 {
        compatible = "bosch,bme280";
        reg = <0>;                       /* CS 片选线 0 */
        spi-max-frequency = <10000000>;  /* 10 MHz */
    };
};

    SPI 总线上 reg 表示第几根 CS 片选线（不是地址）。

    I²C 显示屏实例（SSD1306）：

    &i2c0 {
    pinctrl-0 = <&i2c0_scl_pb6 &i2c0_sda_pb7>;
    pinctrl-names = "default";
    status = "okay";

    ssd1306@3c {
        compatible = "solomon,ssd1306fb";
        reg = <0x3c>;        /* I²C 7-bit 地址 */
        width = <128>;
        height = <64>;
        reset-gpios = <&gpiob 8 GPIO_ACTIVE_LOW>;
    };
};

    I²C 总线上 reg 表示设备的 7-bit 地址。

    CAN 总线设备的特殊性：

    CAN 总线上的设备通常不在 devicetree 中描述，因为 Zephyr 没有像 I²C/SPI 那样的"CAN 设备"总线模型。只有 CAN 控制器本身在 devicetree 中配置，CAN 上的设备在应用层用 SocketCAN 通信。

    /* 只有 CAN 控制器在 devicetree 中 */
&can1 {
    pinctrl-0 = <&can1_rx_pd0 &can1_tx_pd1>;
    pinctrl-names = "default";
    bitrate = <500000>;
    status = "okay";
};

/* CAN 上的设备不在 devicetree 中，应用层用 socket CAN */
int sock = socket(PF_CAN, SOCK_RAW, CAN_RAW);
/* 直接与总线上的设备通信 */

    如果完全自定义一个新设备（没有现成 binding）：

    在项目 dts/bindings/ 下自己写 YAML：

    # <project>/dts/bindings/my-company,my-sensor.yaml
description: My custom sensor
compatible: "my-company,my-sensor"
include: [i2c-device.yaml]

properties:
  my,range:
    type: int
    default: 1000
  rdy-gpios:
    type: phandle-array

    驱动中用 DT_PROP() 宏读取这些属性值。
